# Agent mode

Agent mode connects the loopback web application to one interactive Codex CLI
session without putting model credentials or execution inside the web server.

## Process ownership

```text
interactive root supervisor
└── persistent mailbox monitor
    ├── fresh image worker
    ├── fresh image worker
    └── fresh image worker
```

- The root owns the conversation, app lifecycle, and provider verification.
- Exactly one persistent monitor owns mailbox recovery, polling, claiming,
  heartbeat, delegation, and terminal publication.
- Every candidate is generated by a fresh bounded worker.
- At most three independent refill workers run together.

Analysis and prompt-card jobs also use fresh, single-purpose workers. They do
not generate images unless the job itself is a challenger or refill.

## Start

```bash
npm ci
npm run codex:play
```

The launcher requests eight total threads by default. Override the total after
`--` or with `DIPTYCH_CODEX_THREADS`; five is the minimum:

```bash
npm run codex:play -- 12
DIPTYCH_CODEX_THREADS=12 npm run codex:play
```

The app is built through `./run-only`, binds to `127.0.0.1`, and advertises:

```text
X-Diptych-Generation-Provider: agent
```

Never let a monitor claim work from a server advertising `mock` or an unknown
provider.

## Durable flow

1. The app writes a complete job to `.local-data/agent-mailbox/pending/`.
2. The monitor atomically claims work and records a heartbeat.
3. A fresh worker writes its handoff beneath `.local-data/agent-work/<job-id>/`.
4. Completion validates the proposal and fully decodes the square PNG.
5. The immutable image is named by SHA-256 under `.local-data/assets/` and
   copied to `output/artifacts/`.
6. The app reconciles the terminal result and archives the mailbox record.

IDs remain tombstoned after archival, so an old job cannot be replayed as new.
Completion and failure operations are idempotent, and opposite terminal
outcomes cannot both win.

## Work priority

Interactive and ordinary work precedes background refills:

1. generated initial pair ownership and recovery;
2. ordinary challenger work;
3. private source-profile analysis;
4. prompt-card editor, blender, and writer work;
5. cached leaderboard-profile analysis;
6. a batch of up to three oldest refills.

When at least three independent refills are pending and three slots are free,
the monitor claims and delegates all three together.

## Recovery

If the CLI or terminal closes, do not delete `.local-data`. Resume with:

```bash
npm run codex:play
```

The monitor first recovers unfinished active work, then enters normal polling.
Already-terminal entries are reconciled without regeneration.

If the app needs a rebuild, let active workers reach terminal publication,
pause new claims, restart through `./run-only`, verify the exact provider
header, and resume the same monitor. Do not create a second monitor.

## Stopping

For a recoverable stop:

1. tell the monitor to claim no new work;
2. let started workers finish when practical;
3. record a stopped heartbeat;
4. stop only the app process started by the session.

Pending and safely interrupted active jobs remain recoverable at the next
launch.

## Optional co-proc notification transport

`CO_PROC_GENERATION_CHANNELS` enables an experimental acknowledged
persistent-channel pool. The durable mailbox remains authoritative and handles
unavailable channels and expired leases. This is shipped as an opt-in transport
stage, not a replacement for the monitor or durable mailbox.

See [Configuration](CONFIGURATION.md) for variables and
[Co-proc agent transport and prompt deck](CO_PROC_DECK_DESIGN.md) for the
explicit shipped/proposed boundary.
